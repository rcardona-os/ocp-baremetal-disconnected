# Sneakernet Mirroring

Red Hat specifically designed the oc-mirror tool to handle this exact scenario using a "mirror-to-disk" workflow. Instead of syncing images over a network to a registry, you pack the OpenShift release, operators, and required images into a massive archive file directly onto an intermediary storage device (like a high-capacity USB drive or external hard disk).Here is how that physical transfer workflow operates in practice:

### ⚠️ Prerequisites & Storage Warning

Before beginning the sneakernet process, ensure your intermediary media (USB drive, external HDD) has sufficient storage capacity. While a base OpenShift release may only take a few gigabytes, adding operators (like OpenShift Data Foundation, OpenShift Virtualization, or Pipelines) can quickly inflate the archive size. **For this deployment it is recommend a drive with at least 500GB of free space** depending on how many operators you mirror.

### 1. Preparing the images

#### Red Hat OpenShift Base Images and Operators

The `ImageSetConfiguration` defines the OpenShift Container Platform release,
Red Hat Operators, and IBM Fusion Access for SAN Operator content that must be
mirrored.

The canonical `ImageSetConfiguration` for this deployment is provided below.
Only that configuration should be used for the actual mirror operation.

#### IBM Fusion Access for SAN

This deployment uses **IBM Fusion Access for SAN as a standalone Operator**.

For OpenShift Container Platform 4.21 or later, IBM supports two deployment models:

  - Fusion Access for SAN integrated with Fusion Data Foundation.
  - Fusion Access for SAN deployed using the standalone Fusion Access for SAN Operator.

This procedure uses the **standalone Fusion Access for SAN Operator** and does not deploy Fusion Data Foundation.

The standalone deployment requires:

  - IBM Fusion Access for SAN Operator.
  - Kernel Module Management (KMM) Operator.
  - Bare-metal worker nodes with SAN-attached storage.
  - Worker nodes connected to the same shared SAN LUNs.
  - A container registry for the GPFS kernel module images generated by KMM.
    If the OpenShift internal image registry is used, it must be backed by
    persistent storage and must not use `emptyDir`. Alternatively, KMM can
    be configured to use an external image registry before the `FusionAccess`
    custom resource is created.
  - IBM Storage Scale components required by the selected Fusion Access release.
  - IBM entitlement credentials for entitled images hosted in `cp.icr.io`.

The Fusion Access Operator package is:

  ```text
  openshift-fusion-access-operator
  ```



 ⚡️ Important: the cp.icr.io credentials must contain the customer's IBM Fusion entitlement. IBM explicitly requires that entitlement for these images [DOCS](https://www.ibm.com/docs/en/fusion-software/2.13.0?topic=images-mirroring-fusion)


#### IBM Connected Side

IBM requires the username to be literally cp, with the customer's IBM entitlement key as the password; the entitlement must include IBM Fusion.

- Authenticate to the IBM Entitled Container Registry

IBM Fusion Access for SAN and IBM Storage Scale use entitled container images hosted in:

  ```text
  cp.icr.io
  ``` 

require authentication with an IBM entitlement key.

IBM also publishes public Operator and component images under:

  ```text
  icr.io/cpopen/..
  ```

- Obtain the IBM entitlement key

Obtain an entitlement key from the IBM Container Software Library using an IBMid associated with the customer's IBM Fusion entitlement.

The entitlement key must provide access to the IBM Fusion Access for SAN and IBM Storage Scale images required by this deployment.

The credentials used for cp.icr.io are:
  ```text
  Registry:  cp.icr.io
  Username:  cp
  Password:  <IBM entitlement key>
```

⚡️ NOTE: The username is always cp. The entitlement key is used as the password.

- Create a persistent authentication file

For `oc-mirror`, use an explicit authentication file containing both the
Red Hat OpenShift pull-secret credentials and the IBM entitlement credentials
required by IBM Fusion Access for SAN.

Create a protected directory:

```bash
mkdir -p "${HOME}/.config/oc-mirror"
chmod 700 "${HOME}/.config/oc-mirror"

export MIRROR_AUTH_FILE="${HOME}/.config/oc-mirror/auth.json"
```

Start from the Red Hat OpenShift pull secret:

```bash
jq . <path-to-redhat-pull-secret>/pull-secret.json \
  > "${MIRROR_AUTH_FILE}"

chmod 600 "${MIRROR_AUTH_FILE}"
```

Add the IBM Entitled Container Registry credentials to the same authentication
file:

```bash
podman login \
  --authfile "${MIRROR_AUTH_FILE}" \
  --username cp \
  cp.icr.io
```

Enter the IBM entitlement key when prompted:

```text
Password: <IBM entitlement key>
Login Succeeded!
```

Using the password prompt avoids placing the entitlement key directly in the
shell command history.

Verify the configured registry entries without displaying credentials:

```bash
jq -r '.auths | keys[]' "${MIRROR_AUTH_FILE}"
```

The file should contain the existing Red Hat/OpenShift registry credentials
from the pull secret and an additional entry for:

```text
cp.icr.io
```

Do not commit `${MIRROR_AUTH_FILE}` to Git.
  
#### Verify IBM entitlement access
 
Authentication to `cp.icr.io` does not necessarily prove that the IBM
entitlement provides access to every entitled image required by IBM Fusion
Access for SAN.

Before starting the mirror, verify access to all `cp.icr.io` images included
in `imageset-config.yaml`:

```bash
while read -r image; do
  echo "Checking ${image}"
  skopeo inspect \
    --authfile "${MIRROR_AUTH_FILE}" \
    "docker://${image}" \
    > /dev/null || exit 1
done < <(
  grep -oE 'cp\.icr\.io/[^[:space:]]+' imageset-config.yaml | sort -u
)
```

All checks must complete successfully before continuing.

If any image returns an authentication or authorization error, stop and verify:

- the IBM entitlement key
- access to the IBM Fusion Access for SAN entitlement
- connectivity to `cp.icr.io`
- access to the specific IBM Storage Scale image that failed

### 2. Mirror to Disk (media, directory on OS, etc)
The connected host must have internet access to all registries referenced by the `ImageSetConfiguration`.

Before performing the real mirror operation, validate that the required OpenShift and Operator content can be resolved.

#### Validate the Operator content

Confirm that the IBM Fusion Access for SAN Operator is present in the OpenShift 4.21 certified Operator catalog:

  ```bash
  oc mirror --v2 list operators \
    --authfile "${MIRROR_AUTH_FILE}" \
    --catalog registry.redhat.io/redhat/certified-operator-index:v4.21 \
    --package openshift-fusion-access-operator
  ```

Confirm the Kernel Module Management Operator:

  ```bash
  oc mirror --v2 list operators \
    --authfile "${MIRROR_AUTH_FILE}" \
    --catalog registry.redhat.io/redhat/redhat-operator-index:v4.21 \
    --package kernel-module-management
  ```

Also verify the OpenShift Virtualization package:

  ```bash
  oc mirror --v2 list operators \
    --authfile "${MIRROR_AUTH_FILE}" \
    --catalog registry.redhat.io/redhat/redhat-operator-index:v4.21 \
    --package kubevirt-hyperconverged
  ```

#### Perform an `oc-mirror` dry run

Create a persistent workspace and cache:

  ```bash
  mkdir -p "${HOME}/oc-mirror-workspace"
  mkdir -p "${HOME}/oc-mirror-cache"
  ```

Run the dry run:

  ```bash
  oc mirror --v2 \
    --config imageset-config.yaml \
    --authfile "${MIRROR_AUTH_FILE}" \
    --workspace "${HOME}/oc-mirror-workspace" \
    --cache-dir "${HOME}/oc-mirror-cache" \
    file:///mnt/usb-drive/mirror-archive \
    --dry-run
  ```

Review the generated image mapping:

  ```bash
  MAPPING="${HOME}/oc-mirror-workspace/working-dir/dry-run/mapping.txt"

  echo "Reviewing resolved Operator and component content..."

  grep -Ei \
    'fusion-access|gpfs|spectrum-scale|kernel-module-management|kubevirt|numaresources|nmstate|ubi9' \
    "${MAPPING}"
  echo
  echo "Validating all explicit additionalImages..."

  FAILED=0

  while read -r image; do
    if grep -Fq "${image}" "${MAPPING}"; then
      echo "PASS: ${image}"
    else
      echo "FAIL: ${image}"
      FAILED=1
    fi
  done < <(
    awk '
      /^[[:space:]]+additionalImages:/ { in_additional=1; next }
      in_additional && /^[[:space:]]+- name:/ {
        sub(/^[[:space:]]+- name:[[:space:]]*/, "")
        print
      }
    ' imageset-config.yaml
  )

  if [ "${FAILED}" -ne 0 ]; then
    echo "ERROR: One or more required additional images are missing from mapping.txt"
    exit 1
  fi

  echo "PASS: All explicit additionalImages are present in mapping.txt"
  ```

The mapping must contain the complete content required by this deployment:

- OpenShift Virtualization
- NUMA Resources Operator
- Kernel Module Management Operator
- Kubernetes NMState Operator
- IBM Fusion Access for SAN Operator
- IBM Storage Scale / GPFS CSI images
- IBM Storage Scale daemon and supporting component images
- IBM Storage Scale Operator and must-gather images
- required UBI9 images

The IBM Fusion Access for SAN Operator must resolve to release `1.2.0-3`,
because the IBM Storage Scale images in this `ImageSetConfiguration` are
the CNSA `v6.0.0.2.1` payload associated with that Fusion Access release.

Do not continue with the production mirror if any of the required content
is absent from `mapping.txt`.

#### Mirror the content to disk

After the ImageSetConfiguration has been validated and the required IBM Storage Scale image set has been confirmed, mirror the content to the removable media:

  ```bash
  oc mirror --v2 \
    --config imageset-config.yaml \
    --authfile "${MIRROR_AUTH_FILE}" \
    --workspace "${HOME}/oc-mirror-workspace" \
    --cache-dir "${HOME}/oc-mirror-cache" \
    file:///mnt/usb-drive/mirror-archive
  ```

The `file://` destination contains the archives and metadata that must be transferred across the air gap.

Verify that the mirror archive was generated:

  ```bash
  find /mnt/usb-drive/mirror-archive \
    -type f \
    -name 'mirror_*.tar' \
    -ls
  ```

Generate checksums before transferring the media:

  ```bash
  cd /mnt/usb-drive/mirror-archive

  cp /path/to/imageset-config.yaml ./imageset-config.yaml

  sha256sum mirror_*.tar imageset-config.yaml > SHA256SUMS
  ```

Keep the `oc-mirror` workspace and cache on the connected host. They should not be treated as temporary files because they are useful for subsequent incremental mirror operations.

### 3. Transfer media to the disconnected environment

Physically transfer the removable media to the disconnected environment and mount it on the host that has access to the target mirror registry.

Before importing any images, verify the integrity of the transferred content:

    ```bash
    cd /mnt/usb-drive/mirror-archive

    sha256sum -c SHA256SUMS
    ```

  #### Import the mirrored content into the disconnected registry

The disconnected host must have network access to the target mirror registry and must trust the registry TLS certificate.

Define the target registry and create a dedicated authentication file:

  ```bash
  export TARGET_REGISTRY="<mirror-registry-hostname>:8443"

  mkdir -p "${HOME}/.config/oc-mirror"
  chmod 700 "${HOME}/.config/oc-mirror"

  export DISCONNECTED_AUTH_FILE="${HOME}/.config/oc-mirror/disconnected-auth.json"
  ```

Authenticate to the disconnected mirror registry:

  ```bash
  podman login \
    --authfile "${DISCONNECTED_AUTH_FILE}" \
    "${TARGET_REGISTRY}"
  ```

Use the mirror registry username and password when prompted.

Import the transferred image archive into the disconnected registry:

  ```bash
  oc mirror --v2 \
    --config /mnt/usb-drive/mirror-archive/imageset-config.yaml \
    --authfile "${DISCONNECTED_AUTH_FILE}" \
    --from file:///mnt/usb-drive/mirror-archive \
    docker://${TARGET_REGISTRY}
  ```
